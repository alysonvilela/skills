# Codebase Design

There is one question underneath most design arguments, and it is not "how many files". It is:

**How much complexity does this interface hide, relative to how much it exposes?**

A module is **deep** when the answer is "a lot, behind very little". It is **shallow** when the interface is nearly as complicated as the thing it wraps. Depth is the whole game. Almost everything else in this file is a way of measuring it.

## The deletion test

Point at a module and ask: *if I deleted this and inlined it into its callers, would the total complexity go up or down?*

- **Up** → the module is deep. It was absorbing something.
- **About the same** → it is shallow. It is a name, not an abstraction, and it is costing you a file, an import, and a lookup for nothing.
- **Down** → it is worse than shallow. It is a middleman, and it is actively hiding the code you actually need to read.

Run this test on every wrapper, every `utils` file, every one-line service, and every interface with a single implementation. Most of them fail it.

## Depth, concretely

Three moves make a module deeper. In any design, ask all three:

**Can I remove a method?** Every public method is a promise. Ten methods that each do a tenth of the job push the sequencing, the ordering, and the error handling back onto every caller — and now every caller re-implements it, slightly differently. One method that does the job is deeper than ten that let you assemble it.

**Can I simplify the parameters?** A parameter is a decision you are refusing to make on the caller's behalf. Some of those are genuinely the caller's. Most are not — they are defaults you did not want to commit to. Every config flag you add is a promise to support both branches forever. Count the callers who pass a non-default value; if it is zero, delete the parameter.

**Can I swallow more?** Retries, pagination, cache invalidation, the difference between the two upstream response shapes, the fact that the third-party API returns 200 on failure — every one of these that leaks out is a thing every caller must now know. Eat it. That is what the module is *for*.

## Where to put the boundary

Put the seam where the **traffic is lowest**. A good boundary is one where a lot happens on each side and very little crosses.

If two modules need to know each other's internals to work — if a change to one reliably forces a change to the other, if they share a data shape neither owns, if you keep passing state back and forth — the boundary is in the wrong place. Move it, or remove it. Two tangled modules are worse than one honest one, because now the tangle is *also* an API.

The corollary is unpopular and true: **a large file with a small interface is better than five small files that all import each other.** File count is not complexity. Coupling is complexity. Splitting a tangle into more files does not untangle it; it just spreads it out and adds imports.

## Pull complexity downward

When there is a hard part, the question is *who suffers*.

The module has one author and many callers. If you can make the module's implementation uglier in order to make every call site simpler, **do it, every time.** That is a trade of one person's discomfort for N people's. It is almost always right, and it is almost always resisted, because the author is the one who feels the cost.

The inverse — a clean, "elegant" module that makes every caller handle three error cases and remember to call `init()` first — is the most common way well-intentioned code becomes miserable to use.

## Design it twice

For any decision that is expensive to reverse, sketch a **second, genuinely different** approach before committing to the first.

Not a strawman. A real one, that you would defend. Then say out loud what each is good at and what each is bad at.

The first design is a hypothesis generated by whatever you last worked on. It is often fine. But you cannot know it is fine until there is something to compare it to, and the comparison takes ten minutes. Skipping it is the single cheapest mistake in software design.

## The tactical / strategic split

**Tactical:** get it working. **Strategic:** get it working *and* leave the design better than you found it.

You cannot be strategic all the time; deadlines are real and some code does not deserve it. But default to strategic, and be honest when you go tactical: say "I'm doing this the quick way because X, and the cost is Y". A codebase does not rot from one big bad decision. It rots from a thousand tactical ones that nobody labelled.

## Smells that mean the design is off

| Smell | What it is telling you |
|---|---|
| One change touches seven files | The concept is smeared. It has no home. |
| One file changes for seven unrelated reasons | Several concepts share a home. Split it. |
| The interface is as complex as the implementation | Shallow. Fails the deletion test. |
| Callers all do the same three lines after calling you | Those three lines belong inside. |
| A config flag with one caller | Speculative. Delete it and the branch it guards. |
| An interface with one implementation, forever | It is a rename, not an abstraction. |
| `utils.ts` | Nothing is named. Things went there to avoid a decision. |
| You must read the implementation to use it | The interface has failed at its only job. |
| Passing the same 4 params everywhere | They are one concept. Give it a name. |

## Report

When you propose a design, say:

- **What it hides** — the complexity that stops being every caller's problem.
- **What it exposes** — the interface, in full. If this is long, say why.
- **The alternative you rejected** — and what it was better at, honestly. There is always something.
- **What it costs** — every design has a bill. Name it, or someone else will find it later.
